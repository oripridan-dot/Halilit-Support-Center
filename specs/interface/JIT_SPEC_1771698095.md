# Spec: Downtime Reporting Feature

**Target:** `frontend/src/features/downtime/DowntimeReporting.tsx`

## Overview
This feature allows operators to report downtime incidents within the Halilit Support Center, replacing the manual spreadsheet-based process. It provides a user interface for logging downtime events, including machine selection, start and end times, a description of the problem, and a resolution status. The data will be stored in the backend database and made available for future reporting and analysis.

## Requirements
- Operators must be able to create new downtime reports, specifying the affected machine, downtime start time, downtime end time (optional, for ongoing issues), and a description of the problem.
- Operators must be able to mark downtime events as "resolved".
- The UI must provide a list of machines for operators to select from. This list should be fetched from the backend.
- Downtime start and end times must be recorded with appropriate timestamps.
- The UI should use the dark theme and consistent styling with the existing Support Center.
- Data should be validated on both the frontend and backend.
- The backend API must be authenticated and authorized.
- The list of machines must be dynamically fetched from the database.
- Error handling should be implemented to gracefully handle invalid inputs or unexpected errors.
- Input fields must be properly labeled and accessible.

## Behavior Scenarios

- **Scenario:** Report a new downtime incident.
  - Input: Operator selects a machine, enters a start time, and provides a description. The end time is left blank, assuming the machine is still down.
  - Outcome: A new downtime report is created in the database with the specified information. The backend returns a DowntimeReportResponse. The UI displays a success message.

- **Scenario:** Report a downtime incident with both start and end times.
  - Input: Operator selects a machine, enters both start and end times, and provides a description.
  - Outcome: A new downtime report is created in the database with the specified information. The backend returns a DowntimeReportResponse. The UI displays a success message.

- **Scenario:** Mark an existing downtime incident as resolved.
  - Input: Operator selects a downtime incident from a list (implemented later), and clicks the "Resolve" button.
  - Outcome: The `resolved` flag for the corresponding downtime report in the database is set to `True`. The backend returns an updated DowntimeReportResponse. The UI updates to reflect the resolved status.

- **Scenario:** Invalid input data.
  - Input: Operator enters an invalid start time (e.g., a future date).
  - Outcome: The frontend displays an error message, preventing the form from being submitted. The backend API returns a 400 Bad Request error with a descriptive error message.

- **Scenario:** Backend API unavailable.
  - Input: Operator attempts to submit a downtime report while the backend API is unavailable.
  - Outcome: The frontend displays a generic error message indicating that the request could not be completed.

## Out of Scope
- Reporting and analysis of downtime data. This will be addressed in a separate feature.
- User authentication and authorization details (assumed to be already implemented).
- Detailed error handling UI (e.g., specific error codes). A generic error display is sufficient for this iteration.
- Real-time updates of downtime status.
