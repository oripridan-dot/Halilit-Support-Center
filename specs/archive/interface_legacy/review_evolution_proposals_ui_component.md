# Spec: Review Evolution Proposals UI Component
**Target:** src/components/strategy/evolution/ReviewEvolutionProposals.tsx

## Overview
This React component provides a user interface for reviewing evolution proposals generated by the Halilit Support Center's dark factory algorithms. It allows users to view proposal details, approve, or reject them, triggering subsequent actions within the system.

## Requirements
- The component must fetch evolution proposals from a backend API endpoint.
- The component must display the proposals in a tabular format with sortable columns (Proposal ID, Creation Date, Proposer, Description, Status).
- Each row should have "Approve" and "Reject" buttons.
- Upon clicking "Approve," a confirmation modal should appear, requiring confirmation before submitting the approval to the backend.
- Upon clicking "Reject," a modal should appear, requiring a rejection reason and confirmation before submitting the rejection to the backend.
- After approval or rejection, the table should automatically refresh its data.
- Display appropriate loading states and error messages.
- Implement pagination for handling a large number of proposals.
- Use React 18, TypeScript, and Tailwind CSS (dark theme, slate-900/blue-500 palette).

## Data Contract

**API Endpoint:** `/api/v1/evolution_proposals`

**Request (GET):**

```json
{
  "page": number, // Optional, default: 1
  "page_size": number, // Optional, default: 10
  "sort_by": string, // Optional, column to sort by (e.g., "creation_date")
  "sort_order": "asc" | "desc" // Optional, default: "asc"
}
```

**Response (GET):**

```json
{
  "proposals": [
    {
      "id": string, // UUID
      "creation_date": string, // ISO 8601 timestamp
      "proposer": string, // User ID
      "description": string,
      "status": "pending" | "approved" | "rejected",
      "details": object // Arbitrary JSON blob containing proposal-specific data
    }
  ],
  "total_count": number,
  "page": number,
  "page_size": number
}
```

**API Endpoint:** `/api/v1/evolution_proposals/{proposal_id}/approve`

**Request (POST):**

```json
{} // Empty body
```

**Response (POST):**

```json
{
  "status": "success"
}
```

**API Endpoint:** `/api/v1/evolution_proposals/{proposal_id}/reject`

**Request (POST):**

```json
{
  "rejection_reason": string
}
```

**Response (POST):**

```json
{
  "status": "success"
}
```

**TypeScript Interface:**

```typescript
interface EvolutionProposal {
  id: string;
  creation_date: string;
  proposer: string;
  description: string;
  status: "pending" | "approved" | "rejected";
  details: any;
}

interface EvolutionProposalsResponse {
  proposals: EvolutionProposal[];
  total_count: number;
  page: number;
  page_size: number;
}
```

## Behavior Scenarios

- **Scenario:** Initial Load
  - Input: Component mounts.
  - Outcome: A loading indicator is displayed while the data is fetched from `/api/v1/evolution_proposals`. The table headers are rendered (Proposal ID, Creation Date, Proposer, Description, Status).

- **Scenario:** Data Loaded Successfully
  - Input: API returns a list of evolution proposals.
  - Outcome: The loading indicator disappears. The table is populated with the evolution proposals. "Approve" and "Reject" buttons are displayed for each pending proposal. Pagination controls are displayed with the correct total count.

- **Scenario:** Approve Button Clicked
  - Input: User clicks the "Approve" button for a proposal.
  - Outcome: A confirmation modal appears, displaying the proposal ID and description and asking for confirmation.

- **Scenario:** Approve Confirmation Submitted
  - Input: User confirms the approval in the modal.
  - Outcome: A loading indicator is displayed within the modal. A POST request is sent to `/api/v1/evolution_proposals/{proposal_id}/approve`. Upon successful response, the modal closes, the table refreshes. Upon error, an error message is displayed in the modal.

- **Scenario:** Reject Button Clicked
  - Input: User clicks the "Reject" button for a proposal.
  - Outcome: A modal appears, displaying the proposal ID and description and a text area for entering a rejection reason.

- **Scenario:** Reject Confirmation Submitted
  - Input: User enters a rejection reason and confirms the rejection in the modal.
  - Outcome: A loading indicator is displayed within the modal. A POST request is sent to `/api/v1/evolution_proposals/{proposal_id}/reject` with the rejection reason in the request body. Upon successful response, the modal closes, and the table refreshes. Upon error, an error message is displayed in the modal.

- **Scenario:** API Error
  - Input: The API returns an error.
  - Outcome: An error message is displayed to the user.

- **Scenario:** Pagination
  - Input: User clicks on a different page number in the pagination control.
  - Outcome: A GET request is sent to `/api/v1/evolution_proposals` with the updated `page` parameter. The table is updated with the new data.

- **Scenario:** Sorting
  - Input: User clicks on a column header to sort.
  - Outcome: A GET request is sent to `/api/v1/evolution_proposals` with `sort_by` set to the column name and `sort_order` toggled between "asc" and "desc". The table is updated with the new data.

## Out of Scope
- User authentication and authorization. This is assumed to be handled elsewhere.
- Detailed design of the confirmation and rejection modals (beyond basic functionality).
- Implementation of the backend API endpoints.
- The "details" field of each proposal in the `proposals` array is treated as an opaque JSON blob. Displaying and interpreting the details is out of the scope of this component.
